The system

A course tutor that answers from the course, and will not do the homework

  • The tutor for CSS 342 and 343, our C++ data structures sequence. In production with students since a June 2026 pilot.
  • Two deliverables in one repo: an offline pipeline that builds each course, and a FastAPI app that serves it through a supervised Claude tutor.
  • Around the chat: a topic map, mastery checks, spaced review, find-my-bug, Teach-Back, exam readiness, and instructor pages.
Opening

The one decision everything else follows from

The model writes the reply.
Ordinary code decides what the reply may contain.

Why not a better prompt

A capable model asked to tutor gives the answer by default. Prompt-only withholding leaks at scale: CS50's duck put code blocks in about 22% of replies despite a no-solutions prompt.

Liu et al. (SIGCSE 2025); Macina et al. (2023)

What that buys

A decision you can table-test, a boundary student text cannot cross, and a definition of compliance you can measure: the reply stayed at or below the ceiling code computed.

Part 1 · Building a course

Two walls

Answer keys stay out at ingest, and stay hidden at retrieval

Wall 1: ingest

  • Exams are counted, recorded as a number, and never read.
  • One name rule, answer_name: solution, answer, soln, quiz, midterm, exam, final, key, with camelCase split ("MidTerm", "hwkey") and exclusions ("keyboard", "monkey").
  • An instructor's Canvas token sees everything, so files students cannot see now (hidden, unpublished, locked, future unlock) are dropped unless asked for.
  • Students' private GitHub Classroom repos are skipped; Discord keeps only the instructors' posts, with no author field.

Wall 2: retrieval

  • Anything that did get indexed and looks like a solution or key is filtered out of find_topic.
  • A search keeps its course's chunks plus the shared ones, but only where the collection is stamped: an older, unstamped store is searched course-blind, never emptied.

And the repo itself

  • CI fails on paths that look like student records, any file over 10 MB, a stray secret, or a jump of 200+ files without a stated reason.

Information flow is the defence

Who sees what

Part 2 · The supervised turn

Untrusted text

Every string a student or instructor wrote is framed as data

# agent/framing.py frame("student_message", text) → <student_message> ... </student_message> # every frame's closing tag inside the text # is neutralised: <\/student_message> head_tail(text, limit) # keeps the head AND the last 1,000 chars, # so padding cannot push the real ask out of view safe_name(display_name) # letters, digits, spaces, ' . -, at most 40
  • 18 frame tags: student message, answer and code, transcripts, drafts, the rolling summary, class materials, exam names, run results, a TA's message, and more.
  • Placement: the rolling summary and sandbox results ride in the user turn, never the system prompt.
  • Instructors too: an exam name or uploaded material reaches every enrolled student's prompt, so it is framed like student text.
  • INJECTION is an intent. It never raises the ceiling, and it forces a three-sample judge.
Part 2 · The supervised turn

The ceiling

Policy as data: a ladder, four bands, and seven steps in order

H0acknowledge and encourage
H1restate or clarify the problem
H2point to the concept or slide
H3a leading question, next step
H4the approach in words, no code
H5a worked example, different problem
H6pseudocode, key lines ___
H7full solution (explain mode only)

Bands: mastery ≥ 0.85 → H2; ≥ 0.70 → H3; ≥ 0.40 → H4; below → H5. Less shown, more scaffolding.

  1. Base: the most permissive band among the goals in scope. No evidence on one goal means H5.
  2. Code floor: an attempt, or a question about the student's code, gets at least H4. Never on a degraded classification.
  3. Escalation: an impasse or a granted "Show me more" adds one, capped at H6, counted from the band and floor, so it cannot ratchet.
  4. Exam review: lifts to H5 in a review window, only if every goal is in range and mastered and the turn has no code.
  5. Lockdown: a goal under a pending mastery check caps the turn at H1.
  6. Explain mode (admin, per course) reaches H7, never past a lockdown or a graded assignment.
  7. Conduct restriction: H1, applied last, so nothing lifts it.

Solution demands and adversarial intents never raise and never tighten the ceiling: route kindly.

Part 2 · The supervised turn

Inside the ceiling

A ceiling on how much is not enough. There is also what.

The conclusion rule

Below H7 the tutor may not state the conclusion (a complexity class, a base case, the buggy line, "your code is right") until the student commits, as a trusted flag records.

The actor and the judge read the same withheld words from one constant, so the two cannot drift apart:

WITHHELD_AT_H4 = "the specific bug, the exact wrong token, or the corrected value"

Moves, fading, and the cold start

  • The strategist picks 1 of 12 moves (elicit a prediction, a worked analogy, a completion problem...). A move that shows content needs a minimum rung.
  • Worked examples fade to completion problems, then full problems, from the last two graded scores.
  • One goal with no evidence pins a turn at H5. So ordinary use has to produce evidence: hence the predict-first probe and offered quick checks.
Part 2 · The supervised turn

The actor

A cached prefix that names no course, and a small per-turn contract

  • Four tools: find_topic (moves the slide panel), get_lecture_outline, get_exercise, evaluate_code (a 0 to 4 score and one hint, never corrected code). The envelope filters which ones the actor gets.
  • Bounded loop: at most three tool rounds. Tool inputs are not trusted; a call stays inside the courses the student may open.
  • One prefix for every course: it names no course, so one cache entry serves them all.
  • Memory: eight messages verbatim; older ones fold into a rolling summary after the reply, in a task of its own.
Part 2 · The supervised turn

Cost is architecture

Caching the prefix: a 1-hour TTL, matched to how students read

Per actor call, ~40K-token prefixCost
Uncached input at $3/M$0.12
Cache read at $0.30/M$0.012
1-hour cache write at 2× input$0.24

Arithmetic on list prices, not measured spend. The write pays for itself on the second cached call within the hour.

  • Why not 5 minutes: students read for longer than that between messages, so a 5-minute entry had always expired.
  • Warm-up: opening the chat page sends a max_tokens=0 request that writes the cache, skipped while the entry is alive.
  • Order matters: cached block first, varying block last, tools declared identically on every call, or the cache never hits.
  • Other levers: small models supervise; the judge runs only on risky turns; a gated turn spends nothing on retrieval.
Part 2 · The supervised turn

Deterministic first

The detector runs on every reply, inside the stream

  • Cuts any C++ block over 4 lines at any rung, and any C++ at all at H4 and below (signatures and blanked templates too).
  • Finds code in fences, tildes, indented blocks, raw <pre>, runs of single-span lines, bare code at the margin, and a block that closes braces an earlier one opened.
  • Decodes base64 runs and flags the ones that decode to C++.
  • Exempt: pseudocode with ___ blanks, four lines or fewer, inline spans in prose.

Streaming without leaking

On routine turns prose streams at once (risky turns are buffered for the judge). Inside a code block, a StreamGate holds tokens until the block closes, then emits it or the line "I'll keep the full code out of this one." A base64 run split across chunks is held too.

About 1,280 lines, pure, no model and no network. The policy, detector and judge tests together are about a thousand cases.

Part 2 · The supervised turn

Model second

The judge reads the draft and the contract, never the student

  • When: solution demands, exam leaks, injections, lockdowns, code-adjacent turns at H4 or below, every escalated turn, graded-assignment turns, every degraded classification. Routine concept chat skips it.
  • What it sees: the envelope, the ladder, the cited slide's title, the redacted draft.
  • Verdict: allow, revise or block, with a rule from a fixed list. High-risk turns take three samples and a majority; ties go strict.
  • Revise once: the actor rewrites with the violation named; failing that, a templated pointer to the slides.

A real verdict, from a local run this week (every model call through the claude CLI, a demo student, no production data):

"The draft shows a complete, compilable function solving a different problem (sumList), which is compliant at H5 as a worked example, but then immediately applies it to the student's own task by naming the exact bug in their insertBack code..." rule: code_reveal · verdict: revise · detector cut: yes

The worked example was allowed. Pointing it at the student's own bug was not.

Part 2 · The supervised turn

Failure is a design input

Fail closed where harm is asymmetric; fail open where silence is the harm

Closed

  • No judge verdict on a high-risk or escalated turn: the reply is withheld ("could not be checked; try again in a minute").
  • A degraded classification: intent becomes OTHER, no code floor, no lifts, a strict detector, a forced judge.
  • Graders never auto-pass a check they could not read.
  • A circuit breaker on supervisor failures: in a full outage every reply is withheld within about 20 seconds, and the operator is emailed.

Open, or soft

  • A routine turn when the judge is down: the tutor still answers, under the detector.
  • Maintenance mode on a database error: it does not lock everyone out.
  • The strategist and the rolling summary are advisory: any failure means no move, no summary.
  • Boot never stops on a missing seed or a migration warning.

Everything observable

The ledger: a row per turn, per model call, per graded answer

# turn_events, three turns from the same local run kind=chat intent=SOLUTION_DEMAND rung_used=5 verdict=allow judged=true tool_rounds=1 kind=chat intent=ATTEMPT rung_used=5 verdict=allow judged=true tool=evaluate_code kind=chat intent=QUESTION rung_used=5 verdict=revise detector_cut=true judge_rule=code_reveal code_review_held=true # plus one row per classify, strategist and judge call, # each priced, with its payer and turn id
  • rung_used is the ceiling enforced, not the rung the reply reached. Measuring the latter is an open problem.
  • One function, ledger.record_call, prices and writes every model call's row. It replaced about 18 hand-written sites.
  • The ledger feeds the admin's Supervision tab, the daily digest, the cost report and the nightly auditor.

Part 3

The learner model

Evidence, mastery, decay, and how they set the ceiling.

From evidence to ceiling

One grade scale, a window of six, a forgetting curve

A well-practised goal (high FSRS stability) barely decays; forgetting raises the ceiling back toward H4 and H5 on its own. Mastery is sticky by design: a bad streak shows through decay and the review clock, not by relocking.

Activity data (page views, slide dwell) only triggers offers, never evidence or a ceiling input. Only a student's first answer per find-my-bug item counts.

Part 3 · The learner model

Getting evidence without a test day

Gates, probes and offered checks

Prerequisite gate

An attempt on a lecture with an unmastered earlier prerequisite may wait behind three questions sampled from that goal's pool of about eight. Two of three passes.

While it waits, the goal is locked down: H1, no retrieval, no exercises, no escalation, a three-sample judge.

Predict-first probe

A conceptual question on a goal with no evidence may first get one prediction question, then the answer at the new ceiling.

At most once per conversation and per goal in 14 days. A probe alone never sets a goal below H4.

Offered quick checks

After a failed exercise, a check with no tries left, or a mostly watched lecture. They set review timing, never the map.

Only one module decides who gets a probe, one which goal, one which offer.

Part 4

Running it

Deploys, money, security, data rights and operations, for one person.

Deploys

Manual, gated, and a boot that never stops on an external

  • Manual deploys: a workflow that refuses a commit the tests have not passed, and drives a maintenance page over the swap.
  • Seeds as release assets: the store and audio land once on the persistent disk; the decks and the mastery bank on every boot. Free egress, no object store.
  • Fail-soft boot: each seed is downloaded with retries, unpacked to scratch, checked, then swapped in, with a marker written last. A failure keeps the previous copy and is reported once the app is up.
  • Migrations at boot: every revision after the baseline is guarded. A column is dropped only one deploy after the models stop mapping it, so a rollback still works.
  • Restarts: a reloaded page reattaches to its running reply; a turn a deploy cuts off is marked interrupted; a 502 shows "restarting" and never eats what the student was typing.
  • The image: non-root, the embedding model baked in, and no compiler.
Part 4 · Running it

Money

Three caps, three payers, one function that decides

Caps

  • A daily turn limit per student and a monthly cap for the class, each with an exam-week value.
  • Per-student dollar quotas by day, week and month, with one extension per period.
  • Students see "about N questions left", never dollars; every refusal says when it lifts.

Who pays, in order

  1. The site's key, within the caps
  2. An instructor's key, for their own rosters, in that course, chat only
  3. The student's own key, with their own ceiling

usage.decide, inside run_turn, alone decides. Keys are encrypted per purpose and decrypted only for a turn.

Development-time estimate, June 2026: about $0.02 to $0.05 a turn, planned at $0.03. Clearing one environment variable is the kill switch.

Part 4 · Running it

Security

Small, boring defences, each with a test

Content Security Policy

Enforced on every response; a fresh nonce per page for scripts, no inline handlers, libraries vendored. HTML only in templates, JSON through |tojson.

Request guard

Before any route: a write from another site is refused (this closes login CSRF), and every path has a body ceiling, checked before a byte is read.

Sign-in

Google, or a 6-digit code. UW's mail scanner opens every link on delivery, so the emailed link opens a Continue page instead of signing in.

Read-only view-as

Staff can see a student's pages; every write is refused, writing GETs are skipped, and the right is re-checked on every request.

The claude CLI, locked down

One launcher: every tool off, no API key in its environment, an empty scratch directory, safe mode. A test fails on any other launch.

What Postgres refuses

SQLite is made to refuse it too in tests; an input sweep posts bad values into every field of every student route.

Part 4 · Running it

Data rights by construction

Export, delete and forget, with one producer each

  • Export: one function builds every data package, and its audience has no default. A table in the erasure scope with no export decision fails a test.
  • Delete: the package is sealed with age before any row goes. Tombstones outlive every backup, so a deletion can be re-applied after a restore.
  • Forget: a daily sweep anonymizes identifiable records a year after the term, keeping de-identified telemetry under a pseudonym.
  • Minimal by construction: activity events carry ids and counts, never text; interests and reply language are fixed codes; logs name students by number; Sentry is scrubbed.
  • Never in a prompt: a roster. Never held: an instructor's Canvas token. Never sent: grades, either way.
  • Class figures: no percentile under five students; staff out of every median.
Part 4 · Running it

Operations

Backups you have restored, and jobs that report in

  • Nightly pg_dump, encrypted with age to an offline key, kept 21 days, plus an off-site copy. The job fails rather than store a readable dump.
  • A monthly restore drill.
  • An ops ledger: every scheduled job reports each run; a lateness check catches a job that never started, which an in-run failure email cannot.
  • Monitoring: an outside uptime probe, Sentry, an email on a burst of tutor failures, and a row for every error page a browser gets.

The single-instance assumption

Process memory holds rate limits, the per-student turn claim, reply buffers a reloaded page reattaches to, grading claims, the supervisor breaker and more, in about two dozen modules.

All of it is listed in one place, and it moves to Postgres before a second instance runs. New in-process state must join the list.

Part 5 · Keeping it correct

Measuring the mechanism

Simulated students at $0, a stronger model at night

The persona simulator

  • 29 literature-grounded student cards (the recursion loop-modeller, the help-avoider, the social engineer, the exam leaker...) at seeded mastery bands.
  • They drive the real run_turn, every model call answered by the claude CLI on a subscription: building an API client raises, and each conversation gets a throwaway database.
  • compare runs two arms that differ by one flag.

The nightly auditor

  • Sonnet re-judges every risky turn of the last day plus a sample of routine ones, and reports under-blocking ("the dangerous direction") and over-blocking ("pushes students to unguarded ChatGPT").
  • It never blocks the live pipeline.

Flags decided by experiment

Judging every code turn was switched off in production after a three-repeat comparison showed more revisions and no safety gain.

Caveat: simulated students learn faster than real ones. On the limits of simulated students: Scarlatos et al. (ACL 2026).

Part 5 · Keeping it correct

How it was built

One developer, many AI coding sessions, and a rulebook

  • Claude Code sessions wrote most of the code: in the week the clone covers, 176 of 316 commits carry a Claude co-author line.
  • CLAUDE.md is the rulebook: 48 one- or two-line invariants, each with a long-form section, updated in the same commit as the behaviour.
  • One topic per pull request, a change note per PR, dated handoff documents so a fresh session can continue, and numbered owner decisions.
  • A pre-deploy review in nine slices, each read against the invariants: about 209 findings. Four reviewers found the same top bug independently.
  • A follow-up by a read-only workflow of 34 agents: sweepers, verifiers, a skeptic, re-checkers and a planner, producing 15 phases.
  • The owner alone writes to production, approves paid calls, deploys and flips switches.

The tests that read the code are what let a large number of AI-authored pull requests land without eroding the architecture.

Part 6

Lessons and open problems

What I would keep

Six lessons

  1. Decisions belong in code, not prompts. The prompt states the rule; a pure function computes it; the detector and judge enforce it.
  2. Keep untrusted text away from the decision makers. Information flow beats clever prompting: the policy core, the strategist and the judge never read the student.
  3. Deterministic first, a cheap model second, a stronger model offline to measure the cheap one.
  4. Fail closed where harm is asymmetric, open where silence is the harm. Write down which is which.
  5. One writer, one launcher, one decider, enforced by tests that read the code.
  6. Facts, not claims, for generated content. A bug item exists only if the sandbox shows it; a bank is saved only if it passes its check.
Part 6 · Lessons

What is still open

The problems I have not solved

Measuring the rung reached

The ledger records the ceiling enforced, not how much a reply actually gave away. Prose that states the answer is a known blind spot of the detector.

Validating the judge

Compared so far only with a stronger model. Blind sheets for human labels exist; the labels do not yet.

Running student code

Off in production: exercises are graded by a model's rubric. A sandbox is built, contained on Linux, and used offline only.

Scale and people

One instance, one persona, one maintainer, no LTI. And no controlled study of whether students learn more.
